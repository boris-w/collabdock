# ADR-009 · 开始审查时在 PR 上加 👀：CollabDock 唯一的 GitHub 写操作

- **状态**：已采纳（Accepted）
- **日期**：2026-11-28
- **演进关系**：修改 `ADR-008`（「CollabDock 只读 GitHub」→「只写这一件事」）
- **落地 PR**：#21（自动开始审查 + 👀 标记）

## 背景

审查交给 Lody 里的 AI 之后，PR 作者在 GitHub 上看不到「已经有人在看了」，可能会再次催促。用户最初想在开始审查时发一条「review 进行中」的评论，审完后不再改动，评论或 Approve 都交给 AI。

评论有三个问题：
- PR 上每条新评论都会给作者和所有关注者发通知和邮件，每轮复审一条会反复打扰。
- 审完后 CollabDock 不再改动，「进行中」会一直挂着，变成过时信息。
- 每轮复审都要额外处理去重。

## 决策

1. 在 Lody 会话派发成功后，CollabDock 用用户自己的 GitHub 账号给 PR 加一个 `eyes`（👀）表情：
   - 由评论里 @你 触发的，加在那条评论上；
   - 其余情况（如「请你 Review」）加在 PR 描述上。
2. 只在派发成功后加，派发失败、被取消时不加；手动开始、自动开始、首轮、复审都加。GitHub 对同一用户同一对象只保留一个同类表情，不会重复。
3. 加表情失败（没权限、网络等）不影响审查结果。
4. 开关「开始审查时在 PR 上标记 👀」默认打开；关掉后 CollabDock 对 GitHub 完全只读。
5. **这是 CollabDock 唯一的 GitHub 写操作。** 审查结论、行内评论、Approve 仍由 Lody 里的 AI 在用户确认后发出，CollabDock 不代发。
6. 安全约束：
   - 评论地址只有在协议、主机、端口都与配置的 GitHub API 地址一致，并且路径是同一仓库的 `/(issues|pulls)/comments/<数字>` 时，才会往它的 `/reactions` 发请求；
   - 否则退回加在 PR 上，绝不把 token 发到其他主机。

## 影响与权衡

- **正面**：作者能直观看到审查已经开始，而且表情不触发任何通知或邮件，也不会过时。
- **负面**：CollabDock 重新需要 GitHub 写权限（加表情，需要 token 带 `repo` / `public_repo` 权限），并以用户身份留下可见痕迹。用户可以随时关掉开关恢复只读。
